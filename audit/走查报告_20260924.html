02 / 结论你说的那个问题确实存在，而且比预想的更严重

后台把咨询单和订单分成两套单据，这个设计是对的。问题是小程序端既没有跟着分开，也没有把两者接起来——它把咨询单当成了唯一的历史记录，订单被塞进最底部的功能入口里，而且状态还是错的。

客人成交之后，在小程序上会同时存在两条关于同一段行程的记录，说的却是两回事：

客人看的位置实际显示数据来自问题
「我的」首屏 · 旅程册瑞士 · 行程已确认 · ¥88,000 ·〔看行程〕咨询单 consult没有任何「该付款了」的信号，没有通往订单的入口
「我的」→ 我的订单DD0216836592 · 待支付 · ¥88,000订单 torder要点两层才找得到；状态还显示错

也就是说：客人在首屏看不到自己有一张待支付的订单，而真正的订单入口排在「个人资料」「常用旅客」这些设置项旁边。反过来，进了订单页也看不到这单的咨询历史从哪来、经过了什么。两条线既没分开，也没打通。

03 / A 类问题客人现在就能看到错的信息（6 个）

A1已签约的订单，在小程序显示「待支付」

后台订单状态里有 contracted（已签约）这个值，库里现在就有 3 张是这个状态。但小程序和服务端的状态中文对照表都没有收录它，于是走进兜底分支，显示成「待支付」。

订单 DD0174928713　库里 status = "contracted"　已付 ¥14,040 / ¥46,800 客人端徽标 →「待支付」　　同一屏下方却写着「已付 ¥14,040」，进度条「✓签约」 （同一个页面里三处自相矛盾，演示账号点进「我的订单」第一眼看到的就是这个）
改法：客人端不要自己维护一张状态表。服务端已经有一套按实收金额推导的口径（后台订单列表用的就是它），客人端直接用同一个推导结果，并补上 contracted 的中文。

A2同一张订单，后台显示「已支付」，小程序显示「部分支付」

后台列表的状态是按实收金额算出来的，小程序拿的是数据库里那个原始字段，两者会打架。

订单 DD0080999146　应收 ¥104,000　已收 ¥104,000（已结清） 库里 status = "deposit" 后台列表 →「已支付」（按钱推导，正确）　　小程序 →「部分支付」（读原始字段，错）
改法：同 A1，客人端与后台共用一套推导。这是同一个根因的两个表现。

A3「签约」「行前准备」「出行」三格进度，真实流程下永远不会亮

客人端把七格进度条的亮灯位置，用订单状态去那七个名字里找位置。但后台真实的订单状态只有六个值，contracted／ready／traveling 不是状态，而是后台用「合同签没签 + 人出没出发 + 资源确认没有」现场算出来的阶段。客人端没有用这套算法。

实测第 9 步：合同已签署（contract_no 已落库）→ 客人端进度条一动不动，停在「付定金」 实测第 11 步：标记出行中（trip_state = 出行中）→ 客人端毫无变化，仍停在「付全款」 结果：客人在小程序上，永远看不到自己已经签约、已经出发
改法：服务端已有现成的阶段算法（后台订单详情在用），把它的结果一起返回给客人端，客人端不要自己算。

A4已取消 / 已退订的订单，进度条跳回第一格「下单」打勾

取消和退订不在那七格里，找不到位置就退回 0，于是「下单」这一格亮着。客人看到的是「已退订」徽标配一个刚下单的进度条。

实测第 16 步：退款审核通过后 DDTEST0002　徽标「已退订」　进度条 → 第 1 格「下单」✓亮起
改法：逆向状态不要复用正向进度条，单独一条「已于 X 月 X 日退订，退款 ¥N 已退回」的收尾说明。

A5接口把成本和毛利返回给客人了

客人侧的订单列表和订单详情，用的是后台那个带利润计算的数据包装函数。页面上没画出来，但接口响应里明明白白。客人在手机浏览器里打开开发者工具，或者任何人抓一次包，就能看到这单我们赚多少。

GET /api/mini/orders?phone=139****1234　实际响应： { "no":"DD0174928713", "amount":46800, "paid":14040, "cost":31824, "profit":14976, "rate":32 } ← 成本 / 毛利 / 毛利率
改法：客人侧的订单接口单独做一层字段白名单，只出客人该看的（金额、已付、状态、行程信息），成本类字段一律不进响应。这条建议优先修，和演示不演示无关。

A6真实客人第一次登录，系统会给他伪造 3 段旅程和 1 张 4.68 万的已签约订单

演示用的自动灌数据逻辑，触发条件是「这个号名下没有咨询单」，而小程序登录页不分场合，一律带上演示标记。所以任何一个新手机号第一次登录，立刻被灌进冰岛、意大利、希腊三段旅程，外加一张已签约、已付定金 14,040 元的订单。

库里现有两个真实手机号（昨天 14:21、14:28 各登录过一次）名下的数据： 139****1004 → 3 张咨询单（冰岛 won / 意大利 taken / 希腊 pending）+ 订单 DD0173271036 ¥46,800 139****4368 → 2 张咨询单 + 订单 DD0173684652 ¥46,800 全部 source=mini_ai、销售=李晴，与演示号的数据一模一样——都是自动灌的，不是真单
改法：演示标记只在演示入口（比如首页那个演示账号快捷登录）带上，正常手机号登录不带。这条要尽快定，否则真给客户试用时会出事。

04 / B 类问题咨询单与订单没分开，也没打通（4 个）

B1「我的」首屏把咨询单当成了唯一的历史记录，订单没有位置

首屏结构是：档案封面 → 旅程（咨询单）→ 心愿清单 → 定制顾问 → 功能入口。订单是功能入口里的第一条小字，和「常用旅客」「发票管理」并列。/api/mini/me 这个接口的返回里根本没有订单数据。

改法：首屏改成两条并列的历史线——「我的咨询」和「我的订单」，各给一个区块，各自显示最近几条 + 查看全部。咨询单负责成交前，订单负责成交后，客人一眼能分清自己有几件事在办。

B2成交后两条记录各说一套，客人不知道该信哪个

咨询单成交后变成 已成交，旅程卡显示「行程已确认」；同时生成的订单显示「待支付」。同一段瑞士行程，首屏说已确认，订单页说待支付，两处都没提到对方。

改法：咨询单一旦成交，旅程卡就不再显示咨询单状态，改为「已生成订单 · 待支付 ¥88,000」并直接点进订单；订单详情反向给一条「本单来自 X 月 X 日的定制需求」的回溯入口。两条线各管一段，交接处互相指向。

B3后台手工建的订单，客人在「我的」页统计不到

首屏那个订单计数，是数「有几张咨询单已经转单」，不是数订单。库里 4 张后台直接建的订单（没有对应咨询单）完全不计入。

stats.order = 咨询单里 order_no 不为空的条数 库里 9 张订单中，4 张 consult_no 为空 → 这 4 张永远不进统计
改法：订单数直接查订单表。同时订单详情里，没有咨询单的那种要能正常显示——现在这种订单点进详情，「定制进度」整块是空的。

B4咨询单在客人端看不到流转明细，订单看不到收款记录

旅程卡只有一行状态文字。后台记得很全（接单、方案确认、派单、报价、成交每一步都有日志），客人端一条都不显示。订单详情那块「定制进度」显示的是咨询单的日志，而订单自己的日志（收款、签约、退款审核）客人看不到——收了他的钱，他在小程序上找不到收款凭据。

改法：咨询单详情页补一条时间线（后台日志过滤掉内部信息后给客人看）；订单详情把收款/退款流水单独列一块，让客人能对上自己付过的每一笔。

05 / C 类问题来源记录不下来（4 个）

你要求区分记录客人从哪个入口来的。现在做不到——8 个不同的咨询入口，全部汇到同一个表单页，落库时来源硬编码成「小程序 · 需求表单」。

客人点的按钮在哪带过去的信息落库来源
咨询定制顾问内容文章底部目的地 + 文章 ID ✓需求表单

提交定制需求我的 · 空态无需求表单
悬浮咨询按钮全局无需求表单

C1产品详情页点咨询，客人看的是哪个产品没记下来

咨询单表里本来就有产品 ID 这个字段，小程序提交时不填。顾问接到单只知道客人想去瑞士，不知道他刚刚在看哪条线路、什么价位。

改法：入口带上产品 ID 并落库，顾问接单时直接显示「客人从〈XX 产品〉发起咨询」。

C2订单详情里点「联系我的顾问」，会新开一张定制需求单

客人想问的是已有订单的事，系统给他建了一张新的定制咨询单。顾问那边凭空多出一张单，还不知道它和哪张订单有关。

改法：订单内的联系入口不走建单，挂到这张订单上留言（订单日志里已有留言接口），顾问在订单里直接回。

C3八个入口来源不分，后台没法看转化

改法：把来源拆开记（内容咨询 / 产品咨询 / 目的地咨询 / 定制师咨询 / 顾问咨询 / 悬浮入口 / 主动提单），并把「从哪个内容或哪个产品来」一起落库。改完后台就能看清哪类内容真正带来咨询。

C4你列的「联系定制师咨询」这个环节，小程序端其实不存在

后台有「定制师对话建单」这条来源，但那是门店定制师在自己后台跟客人聊出来的。小程序端点「找他定制」还是跳到填表单，没有真正的对话入口。客人不能在小程序里直接和定制师说话。

改法：这是一块新功能，不是修 bug。建议单独排——小程序端做一个咨询会话页，接到后台定制师那条对话线上（数据结构现成的，对话表已经在用）。

06 / D 类问题客人侧动作全缺，逆向流程走不通（4 个）

后台这部分做得相当扎实：收款有超额校验、取消必须填原因、已收款不许直接取消要走退款、退款走「申请 → 审核 → 出账」两段式、每一步都写流水和日志。问题是——这些全是销售在后台操作，客人在小程序里一个动作都做不了，操作人默认还写死是「李晴」。
环节后台客人侧（小程序）
支付✓ 收款接口完备，校验到位没有支付入口。订单写着「待支付」，客人点不了任何按钮
取消订单✓ 完备没有入口
申请退款✓ 两段式审核完备没有入口
退款进度✓ 状态、金额、审核意见都有完全不显示。实测申请退款后，客人端徽标还是「部分支付」

D1–D4我的建议：客人侧只开三个动作，其余留在后台

  • 去支付——待支付/部分支付时露出按钮。演示环境做成模拟支付（确认即视为收款，走的还是后台那个收款接口，流水一样落库），不接真实支付通道。
  • 申请取消 / 退款——客人提交申请和原因，不直接改订单状态，而是落成一条待处理申请，由门店在后台审。逆向流程涉及钱，不能让客人一键完成。
  • 看退款进度——申请中、审核通过、已退回三态，配金额和时间，客人随时能查。
为什么不全开：后台的校验逻辑（扣费、审核、供应商结算）是这套系统的价值所在，客人侧只做「发起」和「查看」，判断权留在门店。这也是携程飞猪的标准做法。

07 / E 类问题数据量上来以后的承载（3 个）

你问的这一条现在还看不出来——演示账号只有 3 段旅程、4 个心愿、1 张订单。但代码是全量返回 + 全量渲染，没有分页、没有上限、没有筛选，客人用满一年就会出问题。

接口 / 页面现在的行为数据量上来会怎样
我的 · 首屏一次返回这个人全部咨询单 + 全部收藏，前端全量渲染50 张咨询单 + 200 个收藏 → 首屏要等接口吐完才出内容，滚动条长到失去意义
我的订单一次返回全部订单同上，且订单结构比咨询单更重
封面图挑选每次请求都全表扫一遍在售产品，用字符串匹配找配图产品上到几百条时，每次进「我的」都要跑一遍全表匹配

E1我建议的分页方案

  • 首屏只给摘要：咨询单和订单各显示最近 3 条，下面一行「查看全部 12 段旅程 ›」；心愿清单显示 6 个（两行三宫格）+「全部 24 个心愿 ›」。首屏接口只取这几条 + 各自总数，不再全量返回。
  • 独立列表页做分页：每页 20 条，滚到底自动加载下一页，加载中/没有更多都有明确提示。
  • 列表页加筛选：订单按「全部 / 待支付 / 进行中 / 已完成 / 已取消」分页签；咨询单按「进行中 / 已成交 / 已结束」分。这是客人找历史记录最直接的方式。
  • 封面图不再全表扫：改成咨询单落库时就把配图记下来，或者直接用这单方案的封面。

E2收藏的产品下架后，从心愿清单里静默消失

客人收藏的产品一旦下架或停售，服务端过滤时直接丢掉，客人的收藏"凭空少了一个"，没有任何提示。

改法：保留卡片，置灰显示「该产品已下架」，给一个移除按钮和一个「找相似」入口。

E3咨询单状态机里「已接单」是个孤儿状态

状态表里有「已接单」，种子数据里也有 3 张是这个状态，但真实流程里门店接单会直接跳到「跟进中」——这个状态永远产生不了。客人端能看到的「顾问已接单」文案，只在演示数据上出现。

改法：二选一，我倾向前者——① 接单后先进「已接单」，顾问开始动作才转「跟进中」，客人能看到更细的进度；② 或者干脆去掉这个状态，种子数据一并改。

08 / 建议的改造顺序分四批，一批交付一次

批次内容覆盖问题为什么排这个顺序
第 1 批状态口径统一 + 成本字段不外泄 + 演示数据不灌真实客人A1–A6这六条是客人现在就能看到的错误信息，其中成本外泄和伪造订单两条有实际风险，先灭掉
第 2 批「我的」首屏拆成咨询单 / 订单两条历史线，两条互相指向；补咨询单时间线与订单收款流水B1–B4你指出的核心问题。要等第 1 批把状态口径理清，否则拆完两条线还是显示错的状态
第 3 批客人侧开「去支付 / 申请取消退款 / 看退款进度」三个动作；来源按入口拆开记录C1–C3、D1–D4链路补完整。来源记录和入口改造在同一批做，改动集中在同一批文件
第 4 批首屏摘要化 + 独立列表页分页与筛选 + 下架收藏处理 + 封面图不再全表扫E1–E3放最后，因为前三批会动同一批页面结构，分页在结构定下来之后做才不会白改

第 4 批的「联系定制师对话」（C4）是新功能不是修 bug，建议单独排一次，不混在这四批里。

09 / 需要你拍板的 5 件事

① 演示支付怎么做？我的建议是做成模拟支付——客人点「去支付」，确认后直接视为收款成功，走的还是后台那个收款接口，流水一样落库。不接微信支付真实通道（演示环境接不了，也没必要）。如果你要给客户演示"真的扫码付款"，那是另一件事，需要单独排。

② 取消和退款，客人能不能一键完成？我的建议是不能——客人只提交申请，门店在后台审。理由是逆向流程涉及扣费和供应商结算，后台的校验逻辑不能绕过。如果你希望演示时能一键走完，我可以加一个后台快速通过的按钮。

③「已接单」这个状态留不留？我倾向留下并补上——接单后先「已接单」，顾问真正开始动作才转「跟进中」，客人能看到更细的进度。要是你觉得没必要，我就把它连同种子数据一起去掉。

④ 首屏两条线，哪条放前面？我倾向订单在前，咨询在后——有待付款、在履约的订单是更紧要的事。但如果你认为定制咨询是这个产品的主线、要突出"我们在给你做方案"这个感觉，那就咨询在前。这个看你对产品调性的判断。

⑤ 真实客人登录还要不要灌演示数据？我的建议是只保留演示账号那一个口子，正常手机号登录不灌。这条如果你同意，我在第 1 批里一起改掉。

10 / 一件要跟你说明的事

走查过程中我操作失误，短暂丢过一批演示数据，已经恢复。
